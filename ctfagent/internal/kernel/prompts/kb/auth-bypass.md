# 认证与授权绕过

## 先分类，再决定花多少时间

| 现象 | 说明 | 打法 |
|---|---|---|
| 任意密码都过 | 密码根本没校验 | **别停**：找真正的授权点（role 从哪来？） |
| 某账号固定报密码错 | 这个账号走真 SQL | `' OR 1=1 LIMIT 1-- -`、`admin'-- -` |
| 所有输入都 500 | 输入进了 SQL 但炸了 | 当注入点打，别绕开 |
| 有 JWT | 看算法与 `kid` | 见下，但**设预算** |
| Cookie 是 base64/JSON | 可能只做编码不做签名 | 直接改 `role`/`is_admin`/`user_id` |

## 万能密码家族

```
' OR 1=1 LIMIT 1-- -
' OR 1=1-- -
admin'-- -
admin' #
' OR '1'='1
') OR ('1'='1
" OR ""="
```

配合：`username=admin&password=x` 与 `username=x&password=x` 两种排列都试。

## 授权层面的常见错误

- **role 由原始输入推导**：SQLi 能绕过密码，但角色仍取自你输入的字符串 —— 此时注入只为拿数据，不为提权
- **只看 JWT 的 email 不看 role**：改 payload 无效但如果只校验 email 存在性，可以伪造
- **前端隐藏**：把按钮/菜单隐藏了，接口没鉴权 —— 直接打接口
- **越权**：`/api/user/1` 改成 `/api/user/2`；`id` 改成数组/对象；UUID 换成自增 id

## JWT：8 次调用预算（硬规则）

> 编解码与常见伪造用 `jwt` 工具一次做完，别每次写脚本：
> `decode`（解 header/payload + 时间字段 + 可疑 claim 提示）、
> `sign`（HS256/384/512，可带 `kid`/`jku`）、`none`（两种 alg=none 变体）、
> `jwks`（把密钥发布成 `oct` JWKS，给 `jku` 自签用）。

按这个顺序试，**一旦某个变体和正常请求返回逐字节相同，就说明没有该分支，立刻停**：

1. 解 header/payload（`alg`、`kid`、`typ`、过期时间）
2. `alg: none` / `None` / `NONE`（签名段留空 / 保留原签名）
3. 弱密钥字典（`secret`、`jwt`、`key`、项目名，再上几千条常见口令）
4. `kid` 注入：路径穿越读文件、空串、`/dev/null`、SQLi（`kid` 进查询时）
5. `jku`/`x5u` 指向自己的 JWKS
6. 算法混淆（RS256 公钥当 HS256 密钥）

**征兆**：所有变体返回**完全一样**的错误页 → 没有可利用分支，转别的方向。
提示语里出现"网关/迁移/升级/运行时限制"时，几乎都在暗示：**去扫端口，不是去打认证**。

## Session / Cookie

- Flask：`session=` 是 base64(JSON)+签名；只改 JSON 会验签失败，但能读出结构作为情报
- PHP：`PHPSESSID` 服务端存；注意 `session.upload_progress`、反序列化 session handler
- 自定义编码：八进制 `\073`、URL 编码、base64、JWT —— 见 `parser-quirks`

## 图形验证码：先看它有没有"跟着 cookie 走"

登录页带验证码时，**不要先 OCR**，先看响应里有没有把验证码和会话一起发下来：

```http
GET /captcha.png
Set-Cookie: session=<base64(JSON 里含 4 位数字)>.<时间戳>.<签名>
```

- Flask 系：`session` 是 `base64url(JSON)` + `.` + 时间戳 + `.` + 签名，
  **第一段直接 base64 解码就能读出现场验证码**（签名只保证不被篡改，不保证不被读）；
- 别的框架同理：验证码常存在 `Set-Cookie`、隐藏域、或服务端 session 文件里
  （PHP 可直接读 `session.save_path` 下的 `sess_<id>`）；
- 读出来之后**必须带着"同一个会话 cookie"去提交**，否则验证码对不上。

## 多 worker / 多实例：同一个验证码只在一个进程里有效

- 反向代理后面挂多个 worker、且每个 worker 用自己的签名密钥/内存态时，
  `GET 验证码` 与 `POST 登录` **可能落到不同 worker**，表现是「验证码错误」或直接 302 回登录页；
- 特征：**约一半请求失败，但每次都换着花样失败**（不是稳定的"密码错"）；
- 对策：**对同一组凭据循环重试 5~10 次**，只要有一次错误不是"验证码错误"就说明流程通了；
  不要因为第一次失败就判定口令错误；
- 重试预算：验证码类登录 10 次以内属于正常成本，超过就把用户名换成从泄露清单里取的那几个。

## 爆破脚本最容易犯的错：把"成功"吞掉了

- **HTTP 客户端默认会跟随 302**：登录成功通常回 `302 → /dashboard`，
  跟随之后你拿到的是一张 200 的正常页面，如果判据是"页面里有没有错误串"，就会**误判成失败**；
- 正确做法：**关闭跟随**（`follow_redirects=false` / `curl` 不加 `-L`），
  判据改成 `状态码 != 200`、或 `Location` 存在、或"最终落地页"是否包含登录后才有的元素；
- 另一个同等致命的错：判据只看"页面长度是否变化"。
  错误页与正常页在**压缩/模板差异**下长度可能一样，改成看**结构差异**（是否有 `Set-Cookie`、是否有跳转）；
- 结论：**同一批口令跑不出结果时，先把判据换成"状态码 + Location"，再跑一遍**，
  经常会发现命中其实早就在第一轮出现过（不要急着重置字典或加大并发）。
