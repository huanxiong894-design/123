# 拿到立足点之后：内网侦察与横向

单点 getshell 往往只是**第一层**。真正的目标常在内网另一台机器上。
顺序永远是：**先看清网络 → 再找本机自带的代理/隧道能力 → 最后才谈横向工具**。

## 一、第一件事：画出网络拓扑

```
cat /etc/hosts; cat /proc/net/route; ip -4 addr; cat /proc/net/arp
```

- 容器环境里 `eth0` 常是编排网段（`172.x`），`eth1` 才是对外网段；
- **网关地址（`/proc/net/route` 的 Gateway，常见 `x.x.x.1`）旁边的 `x.x.x.2/3/4` 多半就是同应用的其他角色**（跳板机、数据库、管理面板）；
- 应用里泄露的"内网地址"（配置、注释、用户清单）**不代表本机可达**，要实测；
- 有些应用内部有第二个网段（面板自己报的 `ip` 与网关），那台机器才是通往下一跳的门。

## 二、本机往往已经带了"隧道工具"

接手一个应用后，先把它自己的**调试/运维接口**找出来（备份目录、`backup/`、`tools/`、
被 robots 屏蔽的目录），常见形态：

| 形态 | 用途 |
|---|---|
| `?action=scan&host=&ports=1,2,3` | 内网端口探测（`fsockopen` 批量） |
| `?action=forward&host=&port=` + base64 body | 单次 TCP 收发（发一段、收一段） |
| `?action=http&url=` | 通用 HTTP 代理（**可直接打内网 Web**） |
| `check_port.php?host=&port=` | 单端口 + banner |

**优先用 `http` 类动作**：它带 `follow_redirects`、能转发 POST body，
等于把一个 SSRF 变成了"交互式浏览器"。用它去访问内网面板的 `/api/*`，
常常一步就拿到配置与密钥。

## 三、内网扫描怎么扫得快

- 别用 `nc -z` 串扫 65535 个端口（几分钟）；**并发非阻塞 connect** 才是正解：
  一个小 C 程序（`socket` + `O_NONBLOCK` + `select`，200ms 超时）扫一台机器几十秒；
- 先用它确认「哪些 IP 活着」，再对活着的机器做全端口；
- 内网 Web 常见端口优先级：`22 80 443 3000 5000 5432 6379 8000 8080 8081 8443 9000 9200`。

## 四、横向到 SSH：凭据从哪来

1. **应用泄露的用户清单**（备份目录里的 `*users*.txt`、配置注释）—— 用户名往往就是这几个；
2. 密码先试：`用户名`、`用户名+123`、`Admin123`、`P@ssw0rd`、公司名/项目名 + 年份；
3. 用**并行**试（每 8~10 个一次 `wait`），每次连接超时压到 3~5 秒；
4. 目标机上往往**没有 ssh 客户端、也没有 sshpass**：
   - 从外部编译一个**静态客户端**（`CGO_ENABLED=0`），
   - `gzip` 后分块 `POST` 上传（找应用的上传点，或临时写一个只做 `file_put_contents(php://input)` 的落地点），
   - 落地后 `gzip -d` 再执行；
5. 登录成功后第一件事：`id; hostname; ls -la /; ls -la ~`，
   再找题目留的目标文件（各层机器上常见同名目录）。

## 五、判断"这条链走没走通"

- 横向成功的标志不是"能连上"，而是**在新机器上读到了新东西**；
- 若新机器上没有任何目标文件，说明这层只是中转，继续看它的 `route` / `hosts` 找下一跳；
- 面板类角色（运维台、管理台）经常**只有配置泄露是入口**，登录口本身是死路 —— 别在爆破上耗太久，
  先把它的 `/api/config`、`/api/status` 一类只读接口翻干净。

## 六、多级链（一题多目标）：每一层固定做四件事

链式题的目标文件通常**分层摆在每台机器上**（入口机、中间业务机、数据机、面板机各一份），
不要拿到一台就死磕到底，按下面的顺序在**每台新机器**上扫一遍：

```bash
id; hostname -I                 # 我是谁、在第几个网段
cat /entrypoint.sh /docker-entrypoint*/*.sh 2>/dev/null   # 启动脚本：作者怎么布置环境，答案在哪一层
cat /root/.bash_history ~/.bash_history 2>/dev/null       # 历史命令：下一跳地址 + 凭据 + 传输命令
ls -la / ; ls -la /home/* ; ls -la /srv /opt /backup 2>/dev/null
find / -maxdepth 3 \( -name "*.zip" -o -name "*.sql" -o -name "*cred*" \) 2>/dev/null
```

- **启动脚本是最好的情报源**：SUID 设置、目标文件权限、数据库初始化、注入的密钥，全在里面；
- **历史命令会直接写出下一跳的地址和要下载的文件名**，照着复现即可；
- 每台机器都先判断「这层的目标文件在不在、能不能读」，读完再决定继不继续跳。

## 七、凭据：优先主题字典，不要用通用表硬撞

- 同一套环境里，各角色常**共用同一批弱口令**（同一个口令在 Web 后台、OA、数据库、SSH 上都成立）：
  在入口拿到一个口令后，**先把它横向到所有已发现的登录口**，再做爆破；
- 产品化的系统用**「产品名/厂商名 + 年份/@数字」**型口令（`<产品>@2023`、`<产品>@123` 一类的构造），
  通用弱口令表往往没有这一条；
- 用户名从**应用自己泄露的清单**里取（通讯录、用户表、备份目录里的 `*users*`），比通用用户表命中率高一个量级；
- 同一个口令在不同协议上**不一定通用**：Web 后台的口令、SSH 的口令、压缩包的口令常常是三个值，
  压缩包口令优先试最简单的数字串。

## 八、速率限制：先假设有封禁，再动手

- 文件/登录类服务常按「**源 IP + 端口**」限速：连续失败若干次后直接 REJECT 十几分钟，
  且**两个源并发会互相拖累**（看起来像"目标挂了"）；
- 因此：**每次只用一个源、串行、失败间隔 ≥1s**；先用少量高概率口令打一轮，
  命中就停，不要接着扫；
- 一旦出现「连接被拒/超时」而端口扫描仍显示 open，**先等 10~15 分钟**再试，不要加大并发；
- 目标容器也可能被大并发扫描打挂，端口全扫只对"必须扫"的机器做，扫一台停一台。

## 九、没有工具时的替代能力（目标机上只有极简环境）

| 缺什么 | 用什么顶 |
|---|---|
| python / nc | 语言自带的 socket 客户端（PHP `stream_socket_client`、bash `/dev/tcp`、perl `IO::Socket`） |
| redis-cli / mysql 客户端 | 手写行协议：先 `AUTH`，再发命令，按 `*`/`$` 头读长度 |
| ssh / sshpass | 若同一网段另有机器带客户端，就**借那台机器当跳板**执行（`ssh -o PreferredAuthentications=password`） |
| curl | 解释器内置 HTTP（`file_get_contents`、`urllib`、`LWP`） |
| 文件下载 | 先把内容 base64 成一行，再分块塞进请求参数（避免换行/引号被过滤） |

## 十、提权：先看 SUID 和启动脚本，再看内核

```bash
find / -perm -4000 -type f 2>/dev/null
```

- 解释器类二进制（python/perl/ruby/php/node）被打上 SUID，等价于**直接读任何只有 root 能读的文件**：
  `python3 -c "print(open('/path','rb').read())"`，不需要写 exploit；
- 提权成功与否的判据是 `os.geteuid()==0`（`id` 里 `euid` 显示原始 uid 是正常的）；
- 不要在 SUID 上折腾内核 exploit，先确认「能否换一个 euid 执行解释器」这条最短路径。
