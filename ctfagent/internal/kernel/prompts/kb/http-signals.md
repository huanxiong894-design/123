# 把 HTTP 响应当成 oracle

## 状态码语义

| 码 | 含义 | 下一步 |
|---|---|---|
| 200 | 正常 | 看长度/内容是否随输入变化 |
| 302 | 跳转 | 看 `Location`，可能是认证通过/未通过的分界 |
| 400 | 参数格式不对 | 参数名或类型错 → 参数名爆破 |
| 401 | **路由存在**，缺凭据 | 找 token/key/header/cookie |
| 403 | **路由存在**，被规则拦 | 头部伪造、路径变形、方法切换、大小写 |
| 404 | 路由不存在 | 换路径；注意假 404 页面 |
| 405 | **路由存在**，方法不对 | 看 `Allow:`，换方法重打 |
| **500** | **输入进了后端但炸了** | **这是信号，不是故障**：SQLi / 模板 / 类型混淆 / 反序列化 |

**最重要的一条**：`500` 经常是最强的注入信号。只要你的某个字符能改变 500 的出现/消失，
就说明输入进了 SQL/模板/解析器，继续加码（引号、括号、注释、时间函数）。

## 差分（differential）比状态码更强

单看一个响应没用，**看"哪个输入让响应变了"**：

```
基线 = 用一个必然不存在的名字/值发一次
然后只报告：状态码变 / 长度差 > 阈值 / 响应体不再包含基线特征串
```

这能一次性从 6000 个候选里挑出真正被消费的那个参数（见 `fuzz`/`paramfuzz` 的 diff 模式）。

## 长度与哈希指纹

- 同一路径不同参数返回不同长度 → 长度就是侧信道（盲注、IDOR、文件读取都吃这个）
- 大量"200"里挑真文件：按 `长度 + 内容哈希` 聚类，与基线同簇的全丢
- 时间差 > 3 倍 → 时间盲注 / SSRF 内网探测 / 命令执行

## 头部也是 oracle

```
Server / X-Powered-By      → 技术栈与版本（决定用哪套 payload）
Content-Type               → JSON 接口 vs 模板渲染
Set-Cookie                 → session 形态（签名? base64? 明文 JSON?）
Allow                      → 该路由支持的方法
WWW-Authenticate           → 认证类型（Basic? Bearer?）
X-Forwarded-*              → 反向代理链（能否伪造来源 IP）
```

## 别只看响应体：响应头里经常直接就有答案

拿到第一个响应时，**先跑一遍头部**，这是零成本的一步，而且很容易直接结束战斗：

| 位置 | 常见内容 |
|---|---|
| `Set-Cookie` | 会话值本身就是答案（会话名带 token 前缀）、被 base64 的 JWT、权限位 |
| `Location` | 跳转目标里带 token / 内部地址 / 用户名 |
| `X-*` 自定义头 | 调试信息、后端主机名、版本、trace id、有时直接是 secret |
| `Server` / `X-Powered-By` | 技术栈，决定后面打什么 |
| `ETag` / `Last-Modified` | 文件存在性、内容指纹（可以用来做 oracle） |
| `Content-Disposition` | 后端生成文件名，可能反映内部路径 |

快速做法：

```bash
curl -sI http://target/          # 只要头
curl -si http://target/ | head -40
```

**同一条响应的头和体都要过一遍「答案前缀」搜索**，别只盯 HTML。

另外两类「看不见的回显」也常直接给出答案：

- 响应体被压缩/分块时，`Content-Encoding` 里藏着后端实现（`gzip` 的站点往往也接受 gzip 请求体 → 见「边界设备」一节）
- 304 / 条件请求：`If-None-Match` 能确认某个资源存在，用来做列举的 oracle
